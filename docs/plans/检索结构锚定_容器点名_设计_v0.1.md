# 检索结构锚定（容器点名）设计 v0.1

开关：`LINGSHU_ANCHOR=1`（默认关闭；与 `LINGSHU_FTS` 独立，LIKE 路径与 FTS 路径都生效）。

## 1. 问题

问句经常显式点名一个**容器**：「第七章在讲什么」「第3次会话里我说了什么」。
字面检索把「第七章」「这一章」「在讲什么」当成普通词项去全库匹配，但容器里的内容不会复述这些字，
召回回来的是别章里碰巧带同样字面的块。

诊断（hive-memory-bench 切B，PR5 口径）：467 条证据漏检 320 条，其中 173 条**所在章已被 top-10 命中、只是块没中**。
点名章节的 16 道题共 86 条证据，漏检 61 条，证据保留率 29.1%。
这是检索把问句的**指向结构**当成关键词造成的问题，与排序公式无关。改 BM25 参数、做 PRF、实体桥、文档扩展都绕不过去（见 #447 的负结果）。

## 2. 机制

1. **写入契约**：写入方用标签 `<kind>:<n>` 标记容器，`kind ∈ {chapter, session}`，例如 `tags=["chapter:7"]`。
   lingshu 的 tags 列原本就是 JSON 数组，不需要改 schema。
2. **查询侧解析**（`retrieval.parse_anchors`）：只认显式写法：
   - 「第N章」「第N回」→ `chapter:N`；
   - 「第N（次/场/轮）会话/对话/聊天」→ `session:N`；
   - 英文 `chapter N`、`session N`。
   
   N 可以是阿拉伯数字，也可以是 1–999 的中文数字。不猜「七章」「上次那次」这类隐式指代。
3. **重排**（`LayeredStore._anchor_rerank`）：取带该标签的节点，用带引号的 JSON 匹配，保证 `chapter:1` 不会误中 `chapter:17`。
   - 有 FTS 时，按容器内 BM25（`FTSIndex.scores_within`，只在容器节点集合内打分）与 Jaccard 用同一个 blend 打分；
   - 无 FTS 时按 Jaccard 加 tag 加成打分。
   
   容器节点排在最前；不足 limit 时，用原排序结果补齐。同分按 `temporal_coordinate`、id 定序。
4. **不变量**：
   - 开关关闭、问句没有锚点、或容器为空时，结果与原路径逐位相同；
   - 容器标签不进全文索引（`_doc` 过滤 `^(chapter|session):\d+$`），否则 `chapter` 的拉丁二元组和单个数字会成为与内容无关的可匹配词项。

不引入可调参数：在切A 上，容器内中心度加权、保留全局 top-k 都不如「容器内相关度直接排序」，所以这两项都没有加入。

## 3. 实测（真实引擎 `store.search_content`，top-10 证据保留 %）

| 口径 | 关 | 开 |
|---|---:|---:|
| FTS+语境，切A（选型集），shuffle | 31.2 | **38.5** |
| FTS+语境，切B（留出），shuffle | 28.5 | **38.8** |
| FTS+语境，切B 全书 23 章入库（同领域干扰） | 25.5 | **34.5** |
| FTS+语境，切B，seq 写入序 | 29.6 | **39.4** |
| 原 LIKE 路径，切B | 17.6 | **30.0** |
| locomo-zh-500（无锚点问句） | hit@10 1.000 / MRR 0.985 | 完全相同 |

- 延迟：p50 增加约 0.3–0.9 ms，即一次标签 LIKE 查询加容器内 BM25。
- 块级命中基本不变，变化在 ±0.3 以内。收益来自把同章里与问句零字面重叠的块拉进来。
- 收益**只集中在点名容器的问句上**，其余问句逐位不变。

## 4. 已知边界

- 依赖写入方打容器标签。没有标签时开关等于不存在，不会自动推断章节。
- 只覆盖显式点名。「上周」「那天」这类相对时间锚点需要会话日期作为参照，留作后续工作，可以结合 `temporal_coordinate` 时间窗来做。
- 同样的思路用在实体上实测是负的：把「X 是个怎样的人物」当作容器，取含 X 的块并按章轮转，切B 从 40.9 降到 40.0–40.3（自建 harness 口径），所以没有并入。实体不是好的容器。
- 容器大于 limit 时，只返回容器内最相关的 limit 条，不会给出整个容器。
